# Rotation and status

`testlane rotate <profile>` changes the account's password **in the app**, through the app's own
API, and updates the vault. `testlane status` reports how old every stored secret is and raises
alerts. Neither ever prints a secret.

**`rotate` is a human command.** The example permission rules deny it to agents on every launcher
(and the Codex snippet forbids it), and there is no MCP tool or HTTP endpoint for it. A scheduled
task that runs **under a human's account** (Windows Task Scheduler, cron) may call it; that is the
intended way to rotate unattended. `status` is read-only and allowed for agents.

See also: [cli.md](cli.md#exit-codes) for the exit codes, [threat-model.md](threat-model.md#t13-rotation-loses-the-live-credential)
for what rotation does not protect against, and
[playbook/08-rotation-and-hygiene.md](playbook/08-rotation-and-hygiene.md) for a rotation routine.

## Configuring a profile

Rotation is strategy-agnostic and driven by profile options (validated at load for
`nextauth-credentials` and `form-post`; `dependent-token` and `app-handoff`
profiles cannot carry them):

| Option | Meaning |
| --- | --- |
| `rotatePath` | Path on the profile origin of the app's password-change endpoint. Required; without it `rotate` refuses (exit 2, audit `rotate-not-configured`). Absolute and protocol-relative URLs are rejected. |
| `rotateMethod` | `POST` (default), `PUT` or `PATCH`. |
| `rotateBodyFormat` | `json` (default) or `form`. |
| `rotateBody` | JSON object string mapping field names to string templates. Placeholders: `{{email}}` (the account email), `{{secret}}` (the current secret, for "change my password" endpoints that ask for it) and `{{newSecret}}` (required somewhere). Any other `{{...}}` is rejected. |
| `rotateVia` | Optional profile whose session (cookies and headers) authenticates the request, e.g. an admin profile for an admin "set password" endpoint. It is signed in through the normal dependency path: **same origin** (scheme, host and port; otherwise exit 2, audit `origin-not-allowed`), non-production, audited as a `session` row with format `internal:rotate:for=<profile>`. Without it the profile's own session is used (same audit format). |
| `rotateEveryDays` | Positive whole number of days (a string, like every option). `status` alerts `rotation-overdue` when the secret is older. |

For example, added to the `options` of `acme:staging:qa` (the endpoint path and body are
illustrative: use whatever password-change API the app really has):

```json
"rotatePath": "/api/me/password",
"rotateMethod": "POST",
"rotateBody": "{\"currentPassword\":\"{{secret}}\",\"newPassword\":\"{{newSecret}}\"}",
"rotateEveryDays": "30"
```

The new secret is **32 random bytes, base64url (43 characters)**, generated by the broker,
registered with the output redactor at once, and placed only in the request body and the store.

## Two-phase design: no outcome loses the live credential

1. Policy first (production refused, exit 2), then the `rotate*` options.
2. An **exclusive per-profile lock** is taken for the rest of the rotation: a create-only file
   `<TESTLANE_HOME>/locks/<base64url profile>.lock` holding `{ pid, ts, token }`, removed when
   the rotation ends (success or failure). While another rotation of the same profile holds a lock
   younger than 15 minutes, `rotate` is refused (exit 2, audit `rotation-in-progress`); an older
   lock is treated as left behind by a crashed process and replaced.
3. If an earlier rotation left a **pending** value (see below), it is settled first: a sign-in with
   the pending value; if the app accepts it, it is promoted; if the app rejects it, a sign-in with
   the current secret; if that works, the pending value is dropped. If neither can be decided
   (network failure, both rejected), `rotate` stops (exit 3, audit `pending-unverified`) and
   changes nothing.
4. The authenticating session is obtained (`rotateVia`, or the profile itself).
5. **Phase 1:** the new value is written to the vault as `pendingSecret` next to the unchanged
   current `secret`, before the app hears of it.
6. **Phase 2:** the request is sent, and the answer decides. The vault changes only after a
   sign-in has shown which value the app accepts, and at most two sign-ins are made:

| App answer | Sign-ins | Vault afterwards | Exit | Audit (`rotate` row) |
| --- | --- | --- | --- | --- |
| 2xx, and the new secret signs in | new | new secret promoted (`storedAt` = now) | 0 | `ok: true` |
| 2xx, but the new secret does not sign in (yet) | new | **both kept**: a 2xx never drops the new value; `pending rotation unresolved` printed | 3 | `unknown-outcome-after-2xx` |
| any other status, and the current secret signs in | current | pending dropped; current kept | 3 | `app-rejected-<status>` |
| any other status, the current secret is refused and the new one signs in (the app applied it and then errored) | current, new | new secret promoted | 0 | `ok: true`, `applied-despite-<status>` |
| network failure, or no sign-in can decide (app unreachable, both refused) | - | **both kept** (`pendingSecret` stays) | 3 | `unknown-outcome` |

On a non-2xx answer the current secret is tried first, so a refused rotation costs no failed
login with the new value. On an unknown outcome the CLI says so: the next `session` or `check`
resolves which value is live, and the next `rotate` settles it for good. If both values are
refused, retry `rotate` later before re-running `store set`.

**Never a false success.** Promotions and drops compare the stored pending value first. If it
changed underneath the rotation (a human `store set`, or another rotation after a stale lock),
`rotate` exits 3 (audit `pending-changed`), overwrites nothing, and, when the app may already use
the new value and the pending slot is empty, keeps that value as pending next to the stored one so
the next sign-in resolves it.

**How a pending value is resolved by ordinary sign-ins.** `session` and `check` (every surface)
try the current secret first. If the app rejects it and a pending value exists, they try the
pending value once (never more than two attempts); when that succeeds it is promoted (audit
`rotate`, `ok: true`, reason `promoted-pending`). When the current secret succeeds while a pending
value exists, the pending value is kept, a `rotate` row with reason `pending-unresolved` is
written, and the CLI prints `warning: pending rotation unresolved for <profile> ...` on stderr
(MCP: `warnings`; HTTP: `X-Agent-Auth-Pending-Rotation: unresolved`). A human `store set`
replaces both values.

## `status` and alerts

`testlane status [--json] [--max-age-days <n>] [--alert]` (MCP `status`, HTTP
`GET /status`) lists every profile in the registry with `environment`, `strategy`, `hasSecret`,
`storedAt`, `ageDays`, `pendingRotation` / `pendingSince`, `override` (account from the overrides
file), `rotateEveryDays`, the applied `maxAgeDays` and `alerts`:

| Alert | When |
| --- | --- |
| `no-secret` | nothing stored |
| `rotation-overdue` | older than `rotateEveryDays`, else `--max-age-days`, else 90 days |
| `pending-rotation` | a pending value older than 1 hour (an interrupted rotation nobody resolved) |
| `legacy-envelope` | a v2 envelope: age unknown (re-run `store set` or `rotate`) |
| `secret-refused` | the stored value is refused (origin/environment mismatch or older format; `refused` names the reason) |
| `store-error` | the store could not be read for this profile (no detail is reported; run `check <profile>` to see the error). The other profiles are still reported |

Production profiles are listed with `hasSecret: false` and no alerts; their store entry is never
read. `status` makes no network request and writes no audit row. With `--alert` it exits 7 when
any non-production profile has an alert (the report is printed either way).

## Scheduling

Run the scheduled task as the **same user** who ran `store set` (the DPAPI and keychain stores are
per-user), from the consuming repo's directory or with `--profiles <file>` before the subcommand,
and label it with `--requester` so the audit log shows who rotated. Windows Task Scheduler:

```bat
schtasks /Create /TN "testlane status" /SC DAILY /ST 08:00 /TR "cmd /c cd /d C:\src\acme-shop && testlane --requester task:status status --alert > %USERPROFILE%\.testlane\status.txt"
schtasks /Create /TN "testlane rotate acme qa" /SC MONTHLY /D 1 /ST 03:00 /TR "cmd /c cd /d C:\src\acme-shop && testlane --requester task:rotate rotate acme:staging:qa"
```

cron (macOS/Linux):

```cron
0 8 * * *  cd ~/src/acme-shop && testlane --requester cron:status status --alert > ~/.testlane/status.txt || echo "testlane: secrets need attention (exit $?)" | mail -s testlane "$USER"
0 3 1 * *  cd ~/src/acme-shop && testlane --requester cron:rotate rotate acme:staging:qa
```

A failed scheduled `rotate` (exit 3) never leaves the profile without a working secret; the next
`status` shows `pending-rotation` if an unknown outcome was not resolved within an hour.
